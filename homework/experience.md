# Домашнє завдання: результати запуску

## HTTP serverless-функція

Функція `loan.overdue` приймає `loan_id`, `days_overdue`, `daily_rate` і `currency`, нормалізує ідентификатор і валюту, потім повертає суму штрафу. Запуск у Floci через API Gateway підтверджено: валідне тіло повернуло HTTP 200 і штраф `2.50 USD`; запит з некоректними полями повернув HTTP 400, а не 502. `make test` пройшов; валідні і невалидні fixtures знаходяться в `events/`. `make smoke` завершився `9/9`, включно з S3-trigger для thumbnail.

## Cold / warm

Команда `make bench` на Floci, 10 викликів `libratrack-webhook`:

- cold: середнє 1071 мс, мінімум 842 мс, максимум 1947 мс;
- warm: середнє 414 мс, мінімум 369 мс, максимум 569 мс.

Floci запускає Lambda в Docker-контейнерах, а AWS використовує Firecracker microVM; абсолютні часи не можна переносити на AWS. Значим тільки локальний результат цієї середи: cold-виклики в середньому заняли приблизно в 2.6 рази більше часу, ніж warm.

## Serverless або постійний сервер

Для LibraTrack я би оставив постійний сервер для основного каталога і API: навантаження ожидано відносно стабільне, а база даних і користувальські HTTP-сесії вигривають від постійних з'єднань і предсказуємої затримки. Serverless підійшов би для нерегулярних фонових завдань, наприклад обробки завантажених обложок або відправлення увідомлень: такі функції масштабуються по подіям і не вимагають постійно роботінних процесів. HTTP-функцію розрахунку штрафу також можна винести в Lambda, якщо її викликають редко і допустим холодний старт. При стабільному високому трафіку вартість постійного сервера може бути нижче оплати кожного виклику, але це залежить від ресурсів і профілю навантаження. Головні ризики serverless тут — затримка cold start, ліміти часу виконання і складніше локальна діагностика розподілених викликів. Я би вибрав смішану архітектуру: постійний Go API для каталога, а serverless — для незалежної обробки подій.
